# results_schema 1.2.0: one chromosome-end rule, a 2 Mb bp cap written into the file, and the BrAPI ids

Status: accepted. Date: 2026-09-27. Decided by research the maintainer delegated to Fable ("ask fable"), questions Q-A, Q-B and Q-E4 of 2026-09-27, taken for the two sibling tools together; backcross records its half in its docs/adr/0028. Revised 2026-09-29, before it was committed: the cM end rule by a second delegated Fable research question, the cap column's name by the joint release decisions of that day (Q3), and three provenance columns added (Q4, docs/adr/0035).

## Context and Problem Statement

Three questions about the weighted RPP and results.csv were open.

**Q-A, chromosome ends.** `core/background.py` gave the first informative marker on a chromosome the full cap's half, `c/2`, whenever no chromosome length was known: under `assembly: none`, on a chromosome the assembly does not place, and in every cM run (the pipeline passes no cM lengths). backcross gives it `min(p, c/2)`. The two tools therefore disagreed at the first marker in exactly those runs. In bp, coordinate 0 is a chromosome end whatever the length table says, so the first marker has a known distance to the start; only the last marker's distance to the end depends on a length. In cM it is not: linkage-map software puts 0 cM at the first marker by construction, so the telomere lies an unknown distance beyond both terminal markers.

The rule was said to follow Flapjack. It does not, at the ends, and should not: Flapjack credits the first marker the full `min(pos, c)` and the last `min(mapLength - pos, c)`, and `ChromosomeMap.sort()` sets `mapLength` to the last marker's position when the map declares none, so its last marker normally gets zero. That is an asymmetry by accident, not a rule to copy (verified in the source: https://raw.githubusercontent.com/cropgeeks/flapjack/master/src/jhi/flapjack/analysis/MabcAnalysis.java and .../data/ChromosomeMap.java).

**Q-B, the bp coverage cap.** The default was 10 cM with a map and 4,000,000 bp without. Flapjack's default is 10 map units with no bp figure (`Prefs.java`: `mabcMaxMrkrCoverage = 10.0d`; https://flapjack.hutton.ac.uk/en/latest/mabc.html gives only cM examples). 4 Mb had no written derivation. 2 Mb has one: backcross docs/adr/0006 translates 10 cM at about 197 kb/cM of soybean euchromatin (Schmutz et al. 2010, https://www.nature.com/articles/nature08670). And a change of default was invisible: a results.csv written before and after it looked the same.

**Q-E4, BrAPI ids.** A dataset loaded from a BrAPI server carries each line's `callSetDbId` and `sampleDbId` on `Dataset.call_sets` (docs/adr/0024), and backcross writes both into all five of its exports. This tool's results.csv and selected.csv did not, so a ranked row could not be traced back to the server record without re-fetching.

## Considered Options

- Chromosome ends: (1) keep the old rule; (2) copy Flapjack's asymmetric ends; (3) one rule in both tools, the first marker bounded by 0 always; (4) as (3) in bp, and in cM both terminal markers get `c/2` whatever their position. Within the cM question, 2026-09-29: (a) keep `min(p, c/2)` under cM, (b) `c/2` at both ends under cM, (c) `min(p, c/2)` if `p > 0` else `c/2`, (d) no credit beyond the terminal markers.
- bp cap: (1) keep 4 Mb; (2) 2 Mb, the only figure with a derivation; (3) no bp default, require the key.
- The cap and ids in the file: (1) documentation only; (2) new fixed columns, a minor schema bump.

## Decision Outcome

**One end rule, in both tools (option 4; (b) of the cM question).** Interior sides are `min(d/2, c/2)`. At the ends:

- the first marker's outer side: min(p, c/2) when positions are in bp, since the assembly origin is a chromosome end (VCF 4.3 places telomeres at POS 0 and N+1); c/2 when positions are in cM, since a linkage map's 0 cM is its first marker, not the telomere, and the distance to the telomere is unknown at both ends;
- the last marker's outer side: min(max(L − p, 0), c/2) when positions are in bp and an assembly length L is known, else c/2.

The cM half rests on how maps are built and read. OneMap builds positions as `cumsum(c(0, mapfun(seq.rf)))`, so its first marker is 0 cM (https://rdrr.io/cran/onemap/src/R/draw_map.R); R/qtl's `shiftmap` and `est.map`'s `offset` ("Defines the starting position for each chromosome") put the origin where the user asks (https://rdrr.io/cran/qtl/man/shiftmap.html, https://rdrr.io/cran/qtl/man/est.map.html); and R/qtl's `calc.genoprob` carries probabilities past the terminal markers only as far as `off.end`, "Distance (in cM) past the terminal markers on each chromosome to which the genotype probability calculations will be carried", default 0 (https://rdrr.io/cran/qtl/man/calc.genoprob.html). Genome-length estimation treats both ends alike (Chakravarti et al. 1991, method 4, Genetics 128:175), and Frisch and Melchinger 2005 model the segments beyond the outermost markers only when the chromosome length is known (https://pmc.ncbi.nlm.nih.gov/articles/PMC1450430/). (a) would mirror Flapjack's end asymmetry and depend on where the map's author put 0; (c) is discontinuous (p = 0.00 gives c/2, p = 0.01 gives 0.01); (d) is Flapjack's `mapLength` default, rejected above. (b) is symmetric and independent of where the map's author put 0. The bp half keeps `min(p, c/2)` because VCF 4.3 states "Telomeres are indicated by using positions 0 or N+1" (https://raw.githubusercontent.com/samtools/hts-specs/master/VCFv4.3.tex), and the contract accepts position 0. This is output semantics only; the input contract is unchanged, and it lands inside the uncommitted schema 1.2.0, so no further version bump.

`marker_weights` applies the rule in both of its branches, the single-marker chromosome and the multi-marker one. Neither tool claims numeric agreement with Flapjack: interior weighting follows Flapjack, and totals differ at chromosome ends by design. The remaining difference between the tools (at most 0.0016 on the soybean NILs, PLAN.md 2026-09-26) is the source of the length, not the rule, and arises only for soybean, since `resolve_assembly` forces `none` for every other crop.

**The bp default is 2,000,000.** `DEFAULT_MAX_COVERAGE["bp"]` moves from 4,000,000 to 2,000,000; the cM default stays 10. 2 Mb is a soybean euchromatic translation of 10 cM, not a Flapjack value; a program on another crop should set `background.max_marker_coverage` itself.

**Schema 1.2.0.** results.csv gains six fixed columns after `crop` and before the dynamic columns and `token_profile`: `call_set_db_id, sample_db_id, background_max_marker_coverage, tool, tool_version, tool_commit`. The fixed prefix grows from 35 to 41 names and the header of an empty file from 36 to 42. selected.csv gains `call_set_db_id, sample_db_id, tool, tool_version, tool_commit` after `crop`, and not `background_max_marker_coverage`. The placement is docs/adr/0016's rule for a minor bump: new fixed columns after `results_schema`, `token_profile` last.

- `call_set_db_id` and `sample_db_id` are filled from `Dataset.call_sets` for a BrAPI dataset and are an empty cell for a file-loaded one, matching backcross (backcross docs/adr/0015, which checked the BrAPI v2.1 schema; the field text was not re-verified on 2026-09-27, when the specification URL returned 404). This narrows docs/adr/0016's `NA` rule: an identifier with no source is an empty cell (0016, amendment 2026-09-27).
- `background_max_marker_coverage` is the cap the weighted model applied, resolved from `max_marker_coverage` or its default, in `background_unit` (`2000000`, `10`). Under `model: count` no cap is applied and the cell is `NA`. Writing the cap is what makes a change of default visible in the file. The column was drafted as `background_max_coverage`; it takes the shared stem `max_marker_coverage` (Flapjack's `mabcMaxMrkrCoverage`, the criteria key `background.max_marker_coverage`), which backcross also adopts, and avoids "gap" because backcross's segments.csv `gap_criterion` is the run-breaking gap (backcross docs/adr/0008; joint release decisions of 2026-09-29, Q3, docs/adr/0035).
- `tool`, `tool_version` and `tool_commit` name the build that wrote the file: `progeny-selector`, `__version__`, and `g` plus the first seven hex digits of the commit, suffixed `-dirty` when tracked files differ from it, `NA` when unknown (docs/adr/0035).

The fixture generator's independent implementation (`scripts/make_fixture.py`, `marker_weights_cm`) applies the same cM rule, `c/2` at both ends, so the `rpp_*_weighted` expectations come from a second implementation rather than from the tool. Hand-built cases in `tests/test_status_metrics.py` pin what both implementations could misread alike: markers at 0.0 and 5.0 cM with cap 10 weigh 7.5 and 7.5, a bp marker at position 0 has no outer side, and a single marker weighs min(p, c/2) + min(max(L − p, 0), c/2) in bp with a known length and c/2 + c/2 in cM. The generator has no bp-weighted expectation, so the 2 Mb default is pinned by hand-derived tests (`tests/test_map_warnings.py`, `tests/test_results_schema.py`).

### Consequences

Good: the two tools agree at the first marker in every run; the bp default has a stated derivation and a stated scope; a results.csv says which cap produced its weighted RPP and which build wrote it; a BrAPI-loaded row leads back to its server record. Weighted RPP in cM equals its results_schema 1.1.0 value in every run, since the 1.1.0 code already gave both cM ends `c/2` (the pipeline passes no cM lengths); the synthetic fixtures, whose weighted expectations are in cM, regenerate byte for byte identical to their 1.1.0 files. Bad: weighted RPP changes for every bp run on a chromosome with no usable length, where the first marker now gets `min(p, c/2)` instead of `c/2`, and bp-weighted runs that relied on the 4 Mb default change too. A reader that took the first 35 columns by position still works; one that took the dynamic columns to start right after `crop` does not, which is why the version is bumped.
