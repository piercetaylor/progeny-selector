This document decomposes milestone M3 (PLAN.md, "Milestones", line 131, as narrowed by "### M3 scope, decided 2026-09-22") plus the one inherited low from M2 (`docs/m2-phases.md:335`, PLAN.md:288) into phases, one commit each. Every commit passes the gates of CLAUDE.md, run with the project venv `.venv/Scripts/python.exe` (the bare `python` on PATH is an unrelated MGLTools 2.7 install). Dates are 2026-09-22. Facts that could not be verified this session are marked "not verifiable here" with the test or run that settles them; every performance figure is "not verifiable here — filled by the phase run". Doers receive one phase's line range and make no design decisions; each phase names its files, functions, exact names and values, edge cases, tests, model, whether the reviewer runs, its acceptance criterion and the CHANGELOG line the main session writes.

Invariants carried from M1 and M2 (`docs/m1-phases.md`, `docs/m2-phases.md`): `core/` pure (arrays and dataclasses in and out, no I/O, no pandas, no Shiny); `io/` validates and serialises; `app/` computes nothing; colours only from `constants`; `pytest` browser-free; screen interface `view(id)` / `server(id, state)`; Conventional Commits; CHANGELOG under `[Unreleased]`, written only by the main session, never by a doer; decisions as MADR ADRs, numbered from `0021` (`docs/adr/` ends at `0020-contract-1.5-crop-schemes.md`); fixture expectations computed by the generator's independent implementation; at most two concurrent implementers on disjoint files; reviewer on every `core/`, `io/`, `model/` and contract diff plus one end-of-milestone pass; doers never run git; no AI attribution anywhere. **M3 introduces no contract version**: `contract/` is not edited, and anything that would need one is listed under "Questions for the maintainer", never placed in a phase. `constants.RESULTS_SCHEMA` stays `"1.1.0"` unless the maintainer answers Q7 otherwise.

Scope, settled and not reopened here: the five items are (1) streaming `read_vcf` to bound memory, (2) measured performance and a limits table for CPython and Shinylive, (3) accessibility review, (4) the three screen-test gaps M1 deferred, (5) a BrAPI loader. Already shipped and struck: Playwright screen tests (`tests/e2e/`, six files) and the shared contract tests (`tests/test_contract_cases.py`, `scripts/check_contract.py`). ## Questions for the maintainer

Each item is a decision the documents do not settle or an inconsistency between PLAN.md, the ADRs, the sibling and the code. Nothing below is resolved silently; the recommendation is what the phases assume unless overruled.

1. **Streaming the parser does not bound analysis memory, and the scope line implies it does.** PLAN.md:131 and the scope block name "streaming VCF parse to bound memory". The code: `read_vcf` today holds a list of per-record `(s, 2)` int8 arrays and then `np.stack`s them (`io/vcf.py:45-90`), a peak of about 2 x the matrix (400 MB at 50K x 2,000). But `core/background.py::rpp` builds three float64 `(m, s)` temporaries (`contrib`, `w2`, their product; lines 73-80), 32 bytes per call against 2 bytes per call in the matrix, so about 3.2 GB at 100 million calls; `core/similarity.py::ibs_to_sample` builds an int64 `(m, s)` through `np.where` plus five bool `(m, s)` arrays (lines 30-48); `core/classify.py::classify` builds four bool `(m, s)` arrays (lines 79-83). The parser is the smaller problem. Recommendation: keep Phase 3 as specified (the parser, the named item), and approve Phase 6, which chunks `rpp`, `ibs_to_sample` and `classify` over sample columns with one constant width and proves bit-identical output. Tradeoff: one more `core/` phase with a reviewer, against a limits table whose 50K x 2,000 CPython row is otherwise likely to read "did not complete" on a laptop, and a Shinylive row that certainly will. Phase 6 is written in full below and is dispatched only if approved. This is not a reopening of the scope: it is what "bound memory" costs.
2. **`next_generation`: what beyond a blank label is refused.** `io/export.py:229-234` stamps the label into ids and the `generation` column unchecked. `contract/data-contract.md` keeps `generation` free text and QC flags `generation_unparsed`. Recommendation: `io/export.py` strips the label and refuses an empty result only; an unparseable label (`Gen3`) is accepted, as it is on input. Alternative: require `core.generation.parse_generation` to succeed, which would reject labels the manifest contract accepts.
3. **Accessibility target and tooling.** No standard is named in PLAN.md or any ADR (checked). `docs/keyboard-walkthrough.md` is the baseline, and its Rank section says the DataGrid "Needs a mouse", while PLAN.md:80 claims "DataGrid supports arrow-key navigation and space/enter selection" — an inconsistency, and under WCAG a Level A failure (2.1.1 Keyboard) in a third-party component. Recommendation: WCAG 2.2 AA as the target; axe-core through the Python bridge `axe-playwright-python` in the existing `e2e` job (runs in CI); a `KNOWN_A11Y_EXCEPTIONS` list, as the sibling's `tests/browser/a11y-axe.test.tsx` has, carrying the DataGrid keyboard limit with a dated ADR line; Lighthouse not used here (it needs the node toolchain the sibling has). Open: whether a keyboard-only path to multi-row selection (for example a text field of sample ids on the Compare screen) is wanted; recommendation: not in M3, recorded as the known exception.
4. **Browser memory method.** `performance.measureUserAgentSpecificMemory()` (what the sibling measured in Chromium, PLAN.md there line 389) requires cross-origin isolation; `tests/e2e/test_shinylive_export.py` serves `site/` with a bare `http.server`. Recommendation: the bench harness serves with `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp`, asserts `crossOriginIsolated` in the page, and fails loudly (exit 3) otherwise. Not verifiable here: whether Shinylive's same-origin iframe and service worker load under `require-corp`. If they do not, the fallback is this question, not a doer choice; the candidates are the Chromium process tree's RSS delta through `psutil` (crude, includes the JS heap) or a figure printed by the app itself (which would make `app/` compute something).
5. **Bench in CI.** The sibling put a hang guard in CI (its m3-phases Q5). Recommendation: no timing in CI here; the two scripts run per milestone on the reference machine, and CI runs only the small `tracemalloc` bound tests of Phases 3 and 6, which are deterministic. Tradeoff: a regression in wall-clock is caught at the next milestone, not the next commit.
6. **BrAPI and Shinylive (CORS).** The Shinylive build runs in a browser tab, so a fetch to a BrAPI server is cross-origin: the server must send `Access-Control-Allow-Origin` for the Pages origin (and allow `Authorization` in the preflight when a token is used), which this app cannot work around; the sibling records the same (`../isoline-browser/docs/adr/0015`, Bad clause 1). Under Pyodide `urllib` has no sockets; the transport would be `pyodide.http.pyfetch`, which is async. Recommendation: in M3 the loader is CPython-only (Phase 7: `io/brapi.py` and the CLI); the Load-screen source card (Phase 8) is dispatched only if approved and, when it is, works under `shiny run` (server-side fetch, no CORS) and shows "not available in the browser build; use the command line" under Shinylive (`sys.platform == "emscripten"`). Shinylive BrAPI waits for a server known to send the headers.
7. **BrAPI provenance columns.** The sibling writes `call_set_db_id` and `sample_db_id` into every export (its ADR 0015 decision 5). Here that is two new fixed columns in results.csv and selected.csv: a minor bump to `results_schema` 1.2.0 under `docs/adr/0016` line 29 (placed after `results_schema`, before `token_profile`), plus `scripts/read_results.R` `col_types` and the `r-reader` job. Recommendation: not in M3 (no schema change this milestone); Phase 7 keeps the ids on `Dataset.call_sets` (a `model/` field, not a contract change, empty for files) and writes `brapi-callsets.csv` from the CLI, so nothing is lost and the columns can be added later without re-fetching. Tradeoff: a results.csv from a BrAPI run cannot be traced back to server ids until the bump.
8. **BrAPI `sample_id` versus `line_name`.** `docs/reference-repos.md:15` says the distinction came from BrAPI. Recommendation: adopt the sibling's rule verbatim (`../isoline-browser/docs/data-formats.md:13`, ADR 0015 decision 4): `sample_id` = trimmed `callSetName` when non-empty and unique in the variant set, else `callSetDbId`, one warning per shared name, a collision after the fallback is an error; `line_name` comes from samples.csv as for files (replicate call sets share a `line_name` there); `sampleDbId` is retained on `Dataset.call_sets`. Grounds: a samples.csv written for backcross then loads here unchanged, which is the point of the shared manifest.
9. **BrAPI `preview=true`.** The spec offers `preview` so a client can size the request first. Recommendation: not used; `/callsets` and `/variants` are fetched in full before the matrix anyway, so the loader knows `n_variants x n_call_sets` before allocating and warns when it exceeds `BRAPI_MAX_CALLS` (the largest CPython case that completed in `docs/limits.md`). Warning, not refusal: an HPC node with more memory than the reference laptop should not be refused, and an out-of-memory failure is loud, not silent. Tradeoff: one more constant to update when the table changes.
10. **BrAPI token transport on the CLI.** Recommendation: `--brapi-token-env VAR` names an environment variable; the token is never a command-line argument (process lists) and never appears in a URL, error, warning or output (sibling ADR 0015 decision 7). Alternative: a token file path.
11. **BrAPI specification citation.** `docs/reference-repos.md:13-15` cites `plantbreeding/API`; the sibling recorded on 2026-09-15 that those paths return 404 and the specification repository is `plantbreeding/BrAPI` (`../isoline-browser/docs/m3-phases.md:238`). The shapes given to this planner (fetched this session "from plantbreeding/API") match the sibling's fixture recorded from test-server.brapi.org, so the content agrees; the citation does not. Recommendation: Phase 7 records the URL actually fetched and its date in `docs/reference-repos.md`, whichever repository that is.
12. **Sibling docs heading.** `../isoline-browser/docs/data-formats.md:9` reads "BrAPI allele matrix (Backcross only, outside the shared contract)"; after Phase 7 "only" is false. A docs-only edit in the sibling, not a contract change. Recommendation: the main session notes it in the sibling's handoff; nothing here edits `../isoline-browser`.
13. **Half-missing GT.** `io/vcf.py::_parse_gt` reads `./1` as `(-1, 1)`; the sibling's BrAPI rule reads a half-missing token as missing (`(-1, -1)`). Downstream both are N: `classify` marks any `-1` as missing (`core/classify.py:79`), and every IBS caller requires both alleles called. Recommendation: Phase 7's `parse_brapi_call` returns `(-1, -1)`, `_parse_gt` is left as is (the fixture and every VCF test stay byte-identical), and ADR 0024 records that the two are equivalent downstream. Alternative: normalise `_parse_gt` too, a behaviour change with no observable effect.
14. **`possible_duplicate` semantics and the silent overlap skip.** PLAN.md:288 calls the family-aware duplicate rule and the "pairs skipped for insufficient overlap" report "probably M3"; the authoritative scope block does not list them. Recommendation: not in M3; carried in the Handoff. Question B (the two-generation real dataset) also stays open and is the maintainer's.
15. **Two passes over a `.gz`.** Phase 3 reads the file twice (count, then fill), so a gzip is inflated twice; the sibling instead grew a builder buffer (its ADR 0012, 1.57 x inflated bytes). Recommendation: two passes, because the bound is then exactly the matrix plus one line and the code is a preallocation rather than a growth policy; the cost is one extra decompression, measured in the table's "parse s (gz)" column. Alternative: a growth buffer at 1.5 x with a retained over-allocation.
16. **Shinylive at 50K x 2,000.** PLAN.md:131 requires only the first two cases in Shinylive. Recommendation: Phase 2 attempts the third and records the outcome ("did not complete within 30 min", "tab out of memory", or the figures), because a documented limit is more useful than a blank.
17. **Stale text to correct at end of milestone** (Phase 9, docs only): PLAN.md:117 "a shared contract test suite with backcross is a later milestone" and CLAUDE.md:35 "M3 in both repos calls for contract tests that pass in both" (both shipped in M2); PLAN.md:102 "0001..0019" (0020 exists; will end at 0024 or 0025); PLAN.md:147 "Pyodide performance and memory for large VCFs are unmeasured"; PLAN.md:80 the DataGrid keyboard claim (Q3); `app/app.py:5` "Status: M2 in progress"; `docs/adr/0002` "Deferred: BrAPI loading" (a dated note pointing at ADR 0024); PLAN.md:121 "about 13 MB of Pyodide" against the measured 44.4 MB site (M1 block) — record the measured figure.

## Phase 3: streaming `read_vcf`

Goal: `read_vcf` parses a VCF within the size of its genotype matrix plus one line, instead of about twice it, with every contract rule, error message and line number unchanged.

**Design decision, made here so no doer makes it.** `Dataset` still materialises a full `GenotypeMatrix` (`calls` int8 `(n_markers, n_samples, 2)`), and `core/` is not touched: every core entry point indexes whole arrays (`classify`, `rpp`, `donor_segment`, `ibs_to_sample`, `pairwise_ibs`), and a chunked representation would rewrite all of them for a gain the parser does not need. The memory bound is met by reading the file twice: pass 1 validates the header and counts data lines; pass 2 fills a preallocated `np.empty((n_records, n_samples, 2), dtype=np.int8)`. Peak is the matrix plus one line's tokens plus the `Marker` and allele lists (about 15 MB at 50K markers). The cost is one extra decompression of a `.gz` (Q15). Analysis memory is a separate matter (Q1, Phase 6).

## Phase 7: BrAPI loader

Goal: a variant set from a BrAPI v2.1 server (Genotyping module, `/callsets`, `/variants`, `/allelematrix`) loads into the same `Dataset` a file produces, on the command line, with `samples.csv` still declaring roles and `markers.csv` applying as for a file; every rule the sibling settled is mirrored so the two tools read one server the same way (`../isoline-browser/docs/adr/0015-brapi-allele-matrix-loader.md`, `src/io/brapi.ts`, `docs/data-formats.md:9-20`).

Primary-source shapes (BrAPI v2.1, `Specification/BrAPI-Genotyping/AlleleMatrix/`, and the sibling's fixture recorded from test-server.brapi.org): `GET /allelematrix` returns `result` with `callSetDbIds`, `variantDbIds`, `variantSetDbIds`, `dataMatrices[]` (`dataType`, `dataMatrixName`, `dataMatrixAbbreviation` — `GT` reserved for the genotype matrix — and `dataMatrix`, rows = variants, columns = call sets, **the transpose of this tool's samples-as-columns VCF habit**), `pagination[]` with one entry per `dimension` (`VARIANTS`, `CALLSETS`; `page`, `pageSize`, `totalCount`, `totalPages`), `sepPhased`, `sepUnphased`, `unknownString`, `expandHomozygotes`. Query parameters used: `variantSetDbId`, `dataMatrixAbbreviations=GT`, `dimensionVariantPage`, `dimensionVariantPageSize`, `dimensionCallSetPage`, `dimensionCallSetPageSize` (the sibling's `brapi.ts:541-551`). `CallSet`: `callSetDbId`, `callSetName`, `sampleDbId`, `studyDbId`, `variantSetDbIds`. `Variant`: `variantDbId`, `variantNames` (an array on the test server), `referenceName`, `start`, `end`, `referenceBases`, `alternateBases`. **`start` is 0-based and `end` exclusive; VCF `POS` is 1-based: `pos_bp = start + 1`.** `POST /search/allelematrix` is not used.

```python
# src/progeny_selector/io/brapi.py (new)
BRAPI_DEFAULT_PAGE_SIZE_VARIANTS = 1000
BRAPI_DEFAULT_PAGE_SIZE_CALL_SETS = 500
BRAPI_REQUEST_TIMEOUT_S = 60
BRAPI_MAX_CALLS = 100_000_000      # the largest CPython case in docs/limits.md that completed; the doer sets it from the table (Q9)
FetchJson = Callable[[str, dict[str, str]], dict]          # (url, headers) -> parsed JSON body; raises DataContractError

@dataclass(frozen=True)
class BrapiSource:
    base_url: str                  # normalised: trimmed, trailing slashes stripped, http(s) only, no userinfo
    variant_set_db_id: str
    token: str | None = None
    page_size_variants: int = BRAPI_DEFAULT_PAGE_SIZE_VARIANTS
    page_size_call_sets: int = BRAPI_DEFAULT_PAGE_SIZE_CALL_SETS

def normalise_base_url(raw: str) -> str                      # DataContractError("BrAPI: base URL must start with http:// or https://") / ("... must not contain a user name or password; use --brapi-token-env")
def parse_brapi_call(token: str, sep_phased: str, sep_unphased: str, unknown: str) -> tuple[int, int]
def variant_position(variant: dict, scheme: CompiledScheme) -> tuple[str, int] | None   # (normalize_chrom(referenceName, scheme), start + 1); None when referenceName or start is absent/null; non-integer start -> DataContractError naming variantDbId
def marker_id_of(variant: dict) -> str                        # first non-empty entry of variantNames (a string counts as one entry; "." counts as empty), else variantDbId
def assign_sample_ids(raw_call_sets: list[dict]) -> tuple[list[CallSetRef], list[str]]
def fetch_call_sets(source: BrapiSource, fetch_json: FetchJson) -> tuple[list[CallSetRef], list[str]]
def fetch_brapi_genotypes(source: BrapiSource, fetch_json: FetchJson, scheme: CompiledScheme = SOYBEAN,
                          marker_map: dict[str, Marker] | None = None) -> tuple[GenotypeMatrix, list[CallSetRef], list[str]]
def urllib_fetch_json(url: str, headers: dict[str, str]) -> dict   # CPython transport: urllib.request, timeout BRAPI_REQUEST_TIMEOUT_S, Accept: application/json
def load_brapi_dataset(source: BrapiSource, samples_path, markers_path=None, crop: str | None = DEFAULT_CROP_ID,
                       fetch_json: FetchJson | None = None) -> Dataset      # fetch_json None -> urllib_fetch_json, resolved at call time
def call_sets_csv_text(call_sets: list[CallSetRef]) -> str      # header sample_id,call_set_name,call_set_db_id,sample_db_id; CRLF as the other writers
```

Rules, each mirrored from the sibling's ADR 0015 with its decision number:

- (D1) **Positions**: `pos_bp = start + 1`; `start` must be an `int` (not `bool`) or a float equal to its floor; a variant without `referenceName` or `start` takes both from `marker_map[marker_id]` when given; with no entry the load fails `DataContractError(f"BrAPI: variant {marker_id} has no position and markers.csv does not list it")`. `end` is read for nothing. `referenceName` is normalised with `normalize_chrom(name, scheme)`; `read_markers(markers_path, scheme=scheme)` receives the scheme.
- (D2) **Marker id** per `marker_id_of`.
- (D3) **Calls**: `parse_brapi_call` splits on `sep_phased` and `sep_unphased` alike (phase ignored); a token equal to `unknown` is `(-1, -1)`; a token without a separator is haploid, read as homozygous `(a, a)`; a token with an unknown on either side is `(-1, -1)` (Q13); more than two parts, or a part that is not a non-negative integer or `unknown`, raises `DataContractError(f"BrAPI: invalid GT {token!r}")`; an index of 127 or more raises (int8). Allele symbols are `[referenceBases, *alternateBases]` when `referenceBases` is a non-empty string, else the index strings `"0", "1", ...` up to the highest index seen at that variant. A GT index beyond the symbol list at a variant with bases raises naming the variant.
- (D4) **Sample id** per Q8: `sample_id = callSetName.strip()` when non-empty and unique among the variant set's call sets, else `callSetDbId`; one warning per shared name: `f"BrAPI: {n} call sets share the name {name!r}; loaded under their callSetDbId: {ids}"`; a collision among the resulting ids raises `DataContractError` naming the id. `CallSetRef(sample_id, call_set_name, call_set_db_id, sample_db_id)` with `""` for omitted fields.
- (D5) **Traceability** per Q7: `Dataset.call_sets` carries the refs (files leave it empty); `brapi-callsets.csv` from the CLI; no results.csv column in M3.
- (D6) **Paging**: `/callsets?variantSetDbId=&page=p&pageSize=` through `metadata.pagination.totalPages` of page 0; `/variants` page 0 without a token, later pages `pageToken=<nextPageToken>` when the previous response gave a non-empty one, else `page=p&pageToken=p` (the test server ignores `page` there; `brapi.ts:325-347`); `/allelematrix` over both dimensions, variant pages outer, call-set pages inner, `totalPages` from `result.pagination[]` of the first page; every cell joined to its variant and call set by `variantDbIds[r]` and `callSetDbIds[c]` of **that response**, never by page position; a repeated `variantDbId` across `/variants` pages, a repeated `callSetDbId` across `/callsets` pages, a repeated id within a matrix page, or a matrix page whose ids were all already filled is `DataContractError("BrAPI: ... repeated ...")` naming the endpoint and page; an id in a matrix page absent from the lists raises naming it; a response without a `GT` matrix raises `"BrAPI: no GT data matrix"`.
- (D7) **Transport**: `urllib_fetch_json` sends `Accept: application/json` and, when `source.token`, `Authorization: Bearer <token>`; the token never appears in a URL, message, warning, log or output; `HTTPError` -> `DataContractError(f"BrAPI: GET {url} returned HTTP {code}")`; `URLError`/timeout -> `DataContractError(f"BrAPI: could not reach {url}: {reason}")`; a body that is not a JSON object -> `DataContractError(f"BrAPI: GET {url}: response is not a JSON object")`.
- (Q9) **Size guard**: after `/callsets` and `/variants`, before allocation, `n = len(variants) * len(call_sets)`; when `n > BRAPI_MAX_CALLS` append the warning `f"BrAPI: {len(variants)} variants x {len(call_sets)} call sets = {n} calls, above the largest measured CPython case {BRAPI_MAX_CALLS} (docs/limits.md)"`. The matrix is `np.full((n_variants, n_call_sets, 2), -1, dtype=np.int8)` allocated once; each matrix page is discarded after it is written in, so memory is the matrix plus one page.
